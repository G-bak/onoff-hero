# 프로젝트 문의 UI

최신 후속 구현은 [Slack 문의 접수](../operations/SLACK-INQUIRY.md)다. 파일 선택 대신 참고 자료 공유 링크를 사용한다. 서버 웹훅·현재 개인정보 안내 버전이 설정되면 수집·이용과 국외 처리위탁에 각각 동의한 뒤 접수한다. 최대 90일 보관·담당 업무명/이메일을 안내하며 실제 테스트 문의 1건의 Slack 성공 응답을 확인했다. 아래 파일 선택·UI만 구현 설명은 최초 작업 이력이다.

최신 변경: 사용자가 상담톡을 나중에 구현하기로 하여 `consultationChatEnabled=false`로 화면에서 숨겼다. 문의 페이지의 상담 버튼과 대화창은 렌더링하지 않으며 빈 공간·키보드 포커스 대상도 남기지 않는다. 기존 컴포넌트·스타일은 보존한다. 프로젝트 문의와 이메일은 유지한다. 아래 상담톡 연결 설명은 최초 구현 이력이다.

2026-09-13. 사용자가 지정한 바탕화면 `프롬프트.txt`의 요청에 따라 기존 상담톡을 보존하면서 별도 프로젝트 문의 페이지를 만들었다. 이번 범위는 UI다. 백엔드·메일 발송·업로드·개인정보 저장·배포는 구현하거나 실행하지 않았다.

- 페이지: http://localhost:5187/inquiry
- 서비스에서 연결한 예: http://localhost:5187/inquiry?service=web&from=services

## 조사와 콘텐츠 결정

회사 정보는 현재 프로젝트의 `lib/services.ts`와 기존 `lib/consultation.ts`를 기준으로 했다. 사용자 지정 이웃 프로젝트 `onoff-website-redesign/app/page.tsx`의 기존 프로젝트 문의는 이메일 바로가기였으며, 별도 문의폼은 없었다. 이웃 프로젝트는 수정하지 않았다.

2026-09-13에 다음 공식 사이트의 실제 문의 항목을 확인했다. 사이트 디자인·문구·개인정보 정책은 복사하지 않았다.

| 참고 | 확인한 구성 | 적용 |
| --- | --- | --- |
| [디피아이](https://www.dpicreativelab.com/contact/) | 서비스 유형, 업체·담당자, 이메일·연락처, 제작 예산, 마감 일정, 문의 내용, 참고 파일 | 서비스 → 프로젝트 내용·예산·일정·자료 → 담당자 정보로 정리 |
| [디파이닝](https://defining.kr/contact) | 프로젝트 분야, 회사·이름·이메일, 연락처, 문의 내용, 동의 안내 | 분야별 문의와 담당자 정보, 문의 검토 단계의 동의 안내 위치 참고 |

온앤오프의 기획·전략, 브랜드·디자인, 웹사이트, 콘텐츠·마케팅, 운영·유지관리 다섯 분야를 단일 서비스 원본에서 가져온다. 분야를 모르는 고객은 ‘상담 후 결정’을 선택한다. 회사·브랜드, 담당자, 이메일, 요청 내용, 서비스 선택을 필수로 두고 연락처·참고 링크·파일·예산·일정은 선택이다. 창업 준비 중인 고객도 작성할 수 있다.

예산은 고객의 희망 범위를 묻는 옵션이며 회사의 정가가 아니다. 프로젝트 전체/월 운영 기준을 구분하고 미정 선택을 제공한다. 납기·응답 시간·성과·수정 횟수를 임의로 약속하지 않는다.

## 화면과 연결

홈페이지의 고정 CTA는 실제 링크 ‘프로젝트 문의’다. `from`에 현재 섹션을 담아 문의 화면에서 돌아오면 해당 지면으로 복귀한다. 서비스 상세의 문의 CTA도 새 페이지로 연결하며 `service`의 유효한 slug만 미리 선택한다. 알 수 없는 서비스나 복귀 값은 무시한다.

문의 화면은 왼쪽 검정 안내 지면과 오른쪽 흰 입력 지면이다. Montserrat/Pretendard, #090A0F·#FFFFFF·#D8FF3E·#343CFF를 사용한다. 제목과 폼은 한 번 등장하고 멈춘다. 작은 화면은 위아래 구성으로 바꾸며 추가 감상 스크롤·3D·이미지 자산을 넣지 않는다. `prefers-reduced-motion`에서 애니메이션을 끈다.

기존 `ConsultationChat`의 내부 코드·안내·조작은 보존했다. 문의 페이지의 ‘실시간 상담톡’ 버튼에서 같은 대화창을 열 수 있다. 기존 준비 중 상태와 비활성 입력·전송을 유지한다. 기본 이메일 문의도 유지한다.

## 동작과 UI 범위

- 서비스 복수 선택, 상담 후 결정의 배타 선택, 예산 기준 선택.
- 필수 항목·이메일·선택 연락처를 검사하고 첫 오류로 키보드 포커스를 이동한다.
- 참고 파일 선택·드래그 앤드 드롭·제거. 최대 3개, 개별 10MB, 안내된 확장자만 허용하며 빈 파일·중복을 처리한다. 파일 객체는 React 메모리에만 보유한다.
- ‘작성 내용 확인’은 요약 대화창을 연다. 수정/닫기/Escape로 돌아와도 입력값은 유지한다. 문의 전송은 비활성 상태이며 접수 완료를 표시하지 않는다.
- 개인정보 안내에는 현재 전송·저장이 없음을 표시한다. 실제 접수 전에 수집 항목·목적·보유 기간과 동의 UI를 확정한다. 타사 보관 기간을 회사 정책으로 가져오지 않았다.
- 로컬/세션 스토리지·쿠키·API·서버 액션·업로드·파일 내용 읽기 없음. 새로고침 시 작성 중 상태는 초기화된다.
- JS 미사용 시 작동하지 않는 폼을 감추고 JS 안내·기존 이메일을 제공해 기본 폼 전송이 발생하지 않게 한다.
- 초기 JavaScript 연결 전에는 입력 fieldset을 비활성화하고 연결 직후 활성화한다. 서버 HTML이 보이는 짧은 순간 입력한 내용이 클라이언트 초기화로 사라지는 것을 막는다. 별도의 지연 시간은 넣지 않는다.

## 유지보수와 검증

`app/inquiry/page.tsx`: 메타데이터와 유효한 경로 매개변수. `app/components/project-inquiry.tsx`: 화면·입력·검토. `app/project-inquiry.css`: 문의 전용 스타일. `lib/project-inquiry.ts`: 옵션·입력 검사·파일 선택 규칙. 공통 Button/Input/Textarea/Dialog를 사용하고 의존성을 추가하지 않았다.

백엔드 연결 시 실제 수신 엔드포인트·서버 검증·첨부 자료 처리·보관 정책을 별도 구현해야 한다. 프런트엔드 파일 형식 검사는 UI 안내이며 서버 검증을 대신하지 않는다.

`npm run ci:build` 통과: 린트·타입·기존 71개 테스트·프로덕션 빌드·CSS·글꼴·자산 검사. 로그는 `outputs/qa/2026-09-13/inquiry/inquiry-ci.log`다. `outputs/qa/2026-09-13/inquiry/inquiry-qa.json` 전체 통과, 브라우저 오류 0건, 변경/전송 요청 0건이다.

실제 UI에서 필수 입력과 오류 포커스, 서비스 복수/미정 선택, 이메일·국제 전화번호, 예산 기준, 파일 선택·형식·10MB·3개 제한·제거, 검토 대화창과 수정·Escape·포커스 복귀, 저장소 미사용, 서비스 상세의 미리 선택, 기존 상담톡, 고정 CTA와 원래 섹션 복귀를 확인했다. 움직임 감소와 JS 미사용도 확인했다.

1920×1080, 1440×900, 1280×720, 1024×768, 768×1024, 390×844, 320×568, 844×390에서 가로 넘침·필드 잘림이 없고 확인 대화창이 화면 안에 들어옴을 검증했다. 화면 캡처는 `outputs/inquiry-*.png`에 보관한다. 브라우저는 Chrome 및 화면 크기 에뮬레이션이며 실제 휴대폰 기기 성능 검증은 아니다. 초기 자동화의 오류 포커스 확인은 다음 프레임을 기다리도록 수정했고, JS 미사용 안내는 Playwright 텍스트 검색의 noscript 제외를 피하여 실제 안내 요소로 검증했다.

최종 확인에서 초기 연결 전 빠른 입력이 사라질 수 있는 문제를 찾아 fieldset 준비 상태를 추가했다. 스크립트 응답을 늦춰 초기 비활성 → 준비 후 활성 → 입력 유지가 동작함을 확인했고, 새로고침 직후 실제 입력·내용 확인도 재검증했다. 이후 전체 빌드를 다시 통과했다.
